# Feature status

What Crossbow's source contains, area by area, and how far each part has been checked. Crossbow is a development prototype, version 0.1.0; nothing here claims Arc parity. The [README](../README.md) has the short version.

**Source only** means the code exists and has been tested in source (unit, SQLite, simulated-frame or stand-in-page tests), not in the running app. Where a part was exercised in the running app, the text says so; those runs used ad-hoc signed macOS development builds, not a Developer ID or notarized release. Anything not described as checked should be treated as unverified.

## Architecture

- **Desktop:** Rust, egui/eframe 0.37 and wgpu 30.
- **Web engine:** Chromium through CEF 154.5.0, rendered off-screen into the native UI. CEF is C++; this project does not implement a new web engine in Rust and does not use Electron.
- **Local library:** SQLite, profiles, spaces, folders, pinned items, favorites, tabs, archive and history.
- **Account and sync (current development implementation):** a separate Rust Cloudflare Worker, D1 accounts and per-account Durable Objects, with custom email-code sign-in. **Browser sign-in with Clerk (development Worker only, source only, 2026-11-01):** where the sync server offers it, Settings → Account shows **Continue in Browser**. Crossbow opens the Clerk sign-in page in your default browser and waits up to 5 minutes for the answer on 127.0.0.1 (port 47231, 47232 or 47233); Cancel and Escape stop waiting at once. The Worker exchanges the code and checks the ID token's signature, issuer, audience, nonce and times; the app holds no Clerk secret and receives no Clerk token. If Crossbow is itself your default browser, the page opens as an ordinary new tab, as any link from another app does: in the Space that Settings → Links picks (by default the most recent Space), with that Space's profile. A site set to a profile, or the setting that opens links from other apps in a Little Window, applies as for any link. The production Worker has no Clerk settings, so production builds still use email codes only. An email that already has a Crossbow account is never merged: sign in with an email code, choose **Link Browser Sign-In…**, and confirm **Link**, which names both emails. The account keeps its id, so its encrypted rows stay readable. Only the session that started a link can confirm it, once, within 5 minutes, and the confirmation names the Clerk email only if Clerk verified it. Once an account has a browser sign-in linked, **Manage Account in Browser** opens your Clerk account page, where Clerk, not Crossbow, changes that sign-in's name, email, password or connected accounts; the sync account's email stays as it is. The development instance's page answered when checked on 2026-11-01; changes made there haven't been tried. Sign Out doesn't end the Clerk session in the browser. Tested only in source against loopback fixtures; a real Clerk sign-in, the exchange on a deployed Worker and the browser handoff are unverified. By default the client sends JSON payloads; it is **not end-to-end encrypted** and contains no password vault. Newer source adds an **opt-in, source-only** foundation for end-to-end-encrypted library rows (XChaCha20-Poly1305 envelopes, a recovery code, OS-keychain key storage, unlock, reset and account-boundary refusal); its known gaps are listed in the [security architecture](security-architecture.md#implemented-source-foundation). It has been tested only in source, with an in-process fake server and an in-memory key store. Every device on an encrypted account should run this version or later: an older version lacks the later reset and unlock repairs, and can keep a pinned item in a profile its Space does not use. It has not been exercised in the native app, against a real Keychain, against a deployed Worker or on two devices, and has had no external security review, so do not describe sync as end-to-end encrypted. Newer source also adds **Delete Sync Data…** in Settings → Account (source only). Once the account email is typed, it deletes this account's library rows and encryption marker from the sync server and moves a per-account sync epoch, so devices still signed in with the old data stop instead of uploading it again. A device signed out at the time uploads its library when it next signs in, as any sign-in does. This Mac keeps its library, sync turns off here, and the account's encryption key and recovery codes are retired. **Turn Sync On…** uploads the library again as a fresh start. A library that was encrypted uploads nothing unencrypted to any account, including another one this Mac signs in to, until encryption is on for that account, with a new code, or you choose to upload without it for that account. An encrypted device that was signed out during the delete retires its old key when it signs in again, and waits the same way. The route is deployed on the development and production Workers since 2026-11-01. On the development Worker, a scripted check with a synthetic account passed: two rows pushed, deleted, an empty readback naming the new epoch, a refused stale push, an accepted push in the new epoch, and a second delete. So did the repository's 18-step `crossbow-e2e`. It has not been run from the desktop app against a deployed Worker, and production was checked only without signing in. Against an older server the app says "This sync server can't delete sync data yet." and changes nothing. Independent source reviews found that, after a delete, signing in to a different account could upload a formerly encrypted library without encryption, and that a device signed out during the delete could bring back the retired key. Both are fixed in source, and later reviews confirmed those fixes and fixes for most of the minor issues found since. **Delete Account…** in Settings → Account follows: after you type the account's email and enter a code sent to it, the sync server deletes the account's synced library, devices, sessions, browser sign-in links and the account itself, and other signed-in devices stop syncing. This Mac signs out and keeps its library. Your Clerk user isn't deleted. The server keeps the email's sign-in challenges until its daily purge, and the AI proxy's daily request count for the account. The route is deployed on the development Worker since 2026-11-01 and was checked there with a disposable account: a wrong confirmation, a wrong code, then the right email with a fresh code, after which the session answered 401. It isn't on the production Worker. The app's side is tested in source only and hasn't been run against a deployed Worker. Against a server without the route, the app says it can't delete accounts yet. In source, unfinished backup and restore copies are now deleted when backups are cleaned, and a deleted profile's site permissions leave the library and its backups. Still open: Clear History is only partly fixed and can still leave some cleared rows readable in the library file (10 of 3,000 cleared addresses in one test), and all of them while another connection is reading, after the window waits about 5 s; two tests still hold recovery codes as plain text; a deleted profile's "Never translate" sites stay in the library and its backups; and Clear History reports every backup cleaned when the Backups folder can't be listed. These aren't fixed yet. Tombstones, row metadata and the local SQLite library stay unencrypted. The target is Clerk identity plus encrypted library sync and a separate encrypted password vault; see the [security architecture and acceptance gates](security-architecture.md). The [v1 protocol](sync-protocol.md) documents the current implementation, not that future guarantee.
- **Open provider foundation:** Rust installation discovery, explicit local-server diagnostics and prompt-only text conversations, with device-local selection per profile. The earlier TypeScript AI Worker is experimental, not a required provider route. Page context, CLI adapters and AI actions remain unimplemented. Native chat qualification is pending.

## Current source capabilities

The code contains a vertical sidebar, spaces and per-space themes, favorites, folders and pinned tabs, Today tabs, archive, search/command bar, split views, Peek, find on page, downloads, Boosts, settings, browser import and account sync. Source presence does not establish that each journey is finished or live-tested.

First-run setup follows an explicit, resumable path:

1. Welcome.
2. Email-code sign-in, or local-only mode.
3. Account confirmation, only after sign-in.
4. Space name, palette, custom gradient stops, appearance and texture.
5. Suggested favorites.
6. Optional Arc or Chrome import.
7. Optional system-default setup.
8. Shortcut practice.
9. Save completion and start browsing.

Themes include Grain, Sand, Denim and Tweed textures with adjustable strength. Onboarding and Settings share the theme editor. Interface text uses locally bundled **Inter**, with medium-weight controls and real variable-font weights; the shared icon renderer uses **Lucide 0.468.0**. Font licenses are in `app/resources/fonts`. A user-selectable Google Fonts picker remains planned.

Each Space can use an **emoji** or a **Lucide icon**. Settings → Spaces has an Emoji/Icons switch, a search field over 176 keyword-tagged emoji and all 1,543 Lucide 0.468.0 icons, and an "Or type an emoji" field that accepts one emoji or up to two letters. The Space context menu offers ten quick emoji, ten quick icons and **More Icons…**, which opens the full picker. The sidebar header, Space switcher, Settings chips and **Move to Space** menu draw the same icon. The choice is saved in the existing Space icon field (`lucide:<name>` for Lucide), so it syncs with the Space and needs no migration. Emoji use the system's colour emoji font. Picker search, pointer and keyboard selection are covered by UI tests at 560 and 1080 px; **the native picker journey has not yet been exercised** in a running build.

In macOS full screen, pages fill the display with no outer margin or rounded corners; windowed mode keeps the 8 px margin and 10 px corners. A development build was checked in native full screen with no tab open (corner captures show no frame); a loaded page in full screen has not been checked natively.

The Space header has a **+** menu with **New Tab** (⌘T), **New Folder** (⌥⌘N) and **New Split View**; right-clicking empty sidebar space opens the same menu, and a Space with nothing pinned shows a "Drag tabs here to keep them" drop row. Pinned items add **Duplicate**, **Add to Favorites**, **Move to Folder ›** and **New Folder with This Tab**. Folders add **New Folder Inside**, **New Tab Inside**, **Collapse/Expand** and **Open All**, which loads only unopened items in the background. Today tabs add **Pin to Folder ›**. Deleting a folder moves its contents up one level. Sidebar rows are reachable with Tab, and Shift+F10 or the Menu key opens the focused row's menu. Library changes are tested by reopening SQLite and replaying the sync changes into a second library, and the menus by simulated pointer and keyboard tests at 640×420 and 1360×860. **Native ⌥⌘N/Shift+F10 key events, Open All page loading and sync through the real server remain unverified**; focus does not yet return to the row after a menu closes.

**Unread badges and hover previews (source only).** A loaded pinned tab or favorite that isn't on screen shows a badge when its title changes. A title that starts with a count, like "(3) Inbox", shows the count, up to 99+; any other change shows a dot, and a collapsed folder shows a dot for anything inside it. Viewing the tab clears it, and badges last only for the session. Resting the pointer on a collapsed folder for a moment, or moving focus to it with Tab, previews its first 8 items. An unloaded pin or favorite shows its title, host and when it was last opened. Hovering never loads a page. Both are switches in Settings → General → Appearance, on by default for each profile on this Mac. Counts placed mid-title (as Gmail does) show only a dot, and service badges that need an account aren't supported.

**Website appearance (source only).** Settings → General → Appearance → **Website appearance** sets Automatic, Light or Dark for the active Space's profile, on this Mac only. Crossbow sets Chromium's own color mode for that profile, which websites read through `prefers-color-scheme`; pages are never restyled. The choice applies when the profile starts and when it changes. Whether open pages follow it without a reload hasn't been checked in the running app; a loopback test page for that check is in `app/tests/fixtures/appearance/`.

**Sites in a chosen profile (source only).** Settings → Spaces lists, under each profile, the sites it opens, with **Remove** and **Add Site…** (one host, optionally with its subdomains). A tab's menu offers **Always Open {site} in {profile}…** and **Stop Opening…**. A new tab for such a site, whether from a page, the page menu, a typed address or history in the command bar, or another app, opens in that profile's most recently used Space. A notice with **Undo** reopens it where it was going; cookies never move. Hold ⌥ with the click, choose **Open Link in New Tab Here**, or press ⇧Return to keep it here. Same-tab navigation never moves. For links from other apps an Air Traffic Control rule wins, and Settings says so beside the site. Rules stay on this device and are deleted with their profile. Tested only in source and simulated frames.

**Site permissions (source only).** When a page asks for the camera, microphone, screen, notifications or another supported permission, a card appears on its tab with **Allow** or **Don't Allow** and **Remember for this site**, one request at a time. A Translate card, a login offer or an address offer waits while a permission card shows on its page or over its place, and takes no clicks for a moment when it comes back. Leaving the page answers Don't Allow without remembering. Choices belong to the profile, stay on this Mac and never sync. A frame asks in its own name ("Embedded on …"), so allowing a site never extends to the frames it embeds. Settings → Privacy → Site Settings lists each profile's choices with Allow, Block or Ask, and **Reset All** behind a confirmation. A blocked indicator appears in the address pill. Restore Data leaves this Mac's choices as they are. Location isn't available in this build. None of this has been run with real devices or macOS permission prompts.

**Content blocking (source tests and one development-build run; 2026-10-31, updated 2026-11-01).** Settings → Privacy → Content Blocking, per profile on this Mac, has two switches, **Block ads and trackers** and **Block cookie banners**, both off by default, each with its own lists. Add a list from a file with **Add List from File…**: Adblock Plus-style rules or a hosts file. With a switch on, a page's requests that match its lists (scripts, images, frames, fonts and others) don't load; the page you open is never blocked. Rules Crossbow doesn't support are counted and skipped. Lists are private copies on this Mac, never synced; a changed or damaged copy is refused and named, and the other lists still work. Third-party rules use a simplified site rule, so sites on a shared host such as github.io count as one site. Requests made before the lists finish loading at launch, and requests from service workers, aren't blocked. It has been tested in source with simulated requests, and once in a development build against the loopback fixture page (below), not against real pages, and has had no independent review yet.

**Built-in lists.** Block ads and trackers comes with EasyList and EasyPrivacy (version 202611010524), built in unmodified; Crossbow never downloads a list, and new versions arrive only with app releases. Settings → Privacy → Content Blocking can turn either off per profile. Lists added from files apply alongside them. No cookie banner list is included. Lists compile in the background at launch and when a switch turns on. Until a list is ready, requests only it would block load and aren't counted; nothing waits for it. Settings shows "Loading…" on that list, and while no list is ready the shield says "Lists are still loading, so nothing is blocked yet." Crossbow applies 93% of EasyList's network rules, 97% of its element hiding rules and 99.9% of EasyPrivacy's network rules. Most skipped rules are $popup and $document rules, hiding rules for example.* sites, procedural filters, and EasyPrivacy's $redirect rules and scriptlets. On pages EasyList's $generichide exceptions name (including 127.0.0.1 and localhost), only that site's own hiding rules apply. The two lists are 3.5 MB of text built into the app. Building the hiding rules takes 12–28 ms on the browser's main thread in a debug build, once per distinct set of lists; release builds and the native app haven't been measured. EasyList and EasyPrivacy by The EasyList authors (https://easylist.to/), used unmodified under CC BY-SA 3.0 (https://creativecommons.org/licenses/by-sa/3.0/).

**Blocking on this site.** While Block ads and trackers or Block cookie banners is on, web pages show a shield in the address pill (or in the top strip when the sidebar is hidden). Its tooltip and menu say how many requests were blocked on the current page, counting each blocked address once: when the browser's preloader and then its parser each ask for the same script or image, it counts once. Past 1,024 addresses on one page, every further block counts. The count starts again at each page load; a request made just as a page starts can be missed, or counted on the new page. A development build counted both requests, 6 where 3 were blocked; the once-per-address count is fixed in source (2026-11-03) and hasn't been rerun in the app. Turn Off Blocking on This Site lets every request load while a tab shows that site, its frames included (by the simplified site rule), and reloads the tab; Turn On Blocking on This Site undoes it. Settings → Privacy → Content Blocking lists the profile's sites with blocking off, each with Remove. They're kept on this Mac only, never synced, and included in the library's local backups; deleting the profile deletes them, from those backups too. A failed save changes nothing and says why; a damaged record leaves blocking on everywhere and says so.

**Element hiding and cookie banners.** The same lists hide page elements: `##selector`, `host##selector` and `#@#` exceptions; procedural and scriptlet filters (`#?#`, `:has-text()`, `:style()`, `+js()`) are counted as unsupported and skipped. Each document, cross-site frames included, gets one style sheet: the rules for every page plus its own host's, never another host's. A page can read it, so a site could learn some of the rules you use. Shadow DOM isn't covered. A sheet holds at most 50,000 rules and 2 MB; Settings counts the rest. Sites with blocking off get no hiding. Block cookie banners hides banners and blocks their scripts but never answers them: no clicks, no cookies set, no consent API calls, so a hidden banner gives no consent. A site that waits for an answer may keep content hidden or scrolling locked, leave consent-gated embeds empty, or show the banner on every visit; turn off blocking on that site to answer it. `cargo xtask blocking-fixture` serves a loopback page and fixture lists for trying this by hand. Slices 2 and 3 (2026-11-01) are tested in source with simulated requests and stand-in pages only; when hiding applies in a real page, whether a banner flashes first, strict CSP pages and out-of-process frames are unverified natively.

On 2026-11-03 a development build ran the fixture page with a disposable data folder. It hid the fixture's ads and cookie banner and kept the banner's script from loading. It turned blocking off and on for the site, and with blocking off, consent was sent only after Reject was clicked. Every setting and list survived a relaunch. The fixture's own ads list blocked no request: its one network rule, `/fixture-ad/$third-party`, is read as an unsupported regular expression. The fixture now uses a rule the parser reads, checked through the parser and matcher in source, not yet in the app. A corrected rule, `/fixture-ad/*$third-party`, blocked the third-party script and image and let the first-party image load. At 640×420 everything fit, but **Content Blocking Settings…** opened Privacy where it was last scrolled rather than at Content Blocking; in source it now opens at the section's top, not yet rerun in the app. Real pages, release builds and exact 1360×860 geometry weren't checked.

**Links to other apps (source only).** Crossbow asks before handing a link to another app ("Open Zoom?"), and a top-level site can be allowed to open links of that type without asking; that grant is listed with **Remove** and cleared by Reset. Links that run scripts, open Terminal, install apps or mount shares, and links whose app runs commands, are always refused. A page that opens such links without a click is throttled. Peek and Little Windows never open other apps. The hand-off to macOS hasn't been run natively.

Settings → Spaces can move a Space to another profile after a confirmation. The library change commits first; only then do the Space's tabs, split panes and Peek close and reopen in the new profile, so sites use that profile's sign-ins. A failed save changes nothing and offers **Retry**. Profiles can be created (optionally for the current Space), renamed inline (trimmed, unique, at most 40 characters) and deleted when no Space uses them and they are not the last one. Deletion asks for confirmation, then removes that profile's favorites, history, archive and its own Chromium folder only; a folder that cannot be removed immediately is purged at the next start. **New Spaces use** picks the profile for new Spaces and lasts until the app quits. Per-profile device settings (downloads folder, AI provider) are not removed with the profile, and archived tabs of a moved Space stay hidden from both profiles. After a complete sync, a pinned item added or edited on another device while its Space moved takes the profile of the newest version of that Space the devices hold, without being rewritten back and forth, and a favorite added elsewhere to a profile deleted here is deleted too. A Crossbow from before this version drops the Space version a pin records. This version then repairs that pin at most once per version and profile of its Space and leaves the older device's choice, so the pin can stay in a profile its Space does not use until the Space changes again. Run this version or later on every device. All of this is tested only in source, between two or three libraries and an in-process fake server. **Real view closing and reopening, folder deletion while Chromium is still writing, and two-device sync remain unverified.**

Settings → Shortcuts lists all 47 browser actions from the same registry that dispatches keys, menu hints and command-bar badges. **Search shortcuts** filters by name and **Press Shortcut** finds the actions bound to a chord without running them. Each action has a primary and an alternate binding: click one (or press Enter on it), press the new chord, or press Delete to clear it; Esc cancels. A chord another action uses names both and offers **Reassign** or **Cancel**. Chords macOS or text editing owns (⌘Q, ⌘H, ⌥⌘H, ⌘M, ⌘Tab, ⌘`, ⌘Space, ⌃⌘Q, ⌃⌘F, ⌘, and ⌘A/C/V/X/Z, ⇧⌘Z), Esc and bare keys other than function keys are refused with a reason. **Reset** restores one action and **Reset All Shortcuts** restores every default after a confirmation. Changes are saved on this device only and are not synced; a failed save keeps the previous shortcuts and offers **Retry Save**. A regression test pins all 49 chords handled before the registry, so default behaviour is unchanged. **Shortcut priority**, at the bottom of the page, chooses **Browser shortcuts win** (the default), **Websites receive shortcuts first** or **Press twice**. In **Press twice**, the first press of a chord the page uses goes to the page, and pressing it again within half a second runs Crossbow's action instead; another chord, a focus change or a navigation in between starts the count again, and if the page ignored the first press Crossbow acts at once. In the second mode, when a web page has the keyboard, a chord goes to the page first. Crossbow runs its own action only if the engine reports the press unhandled within two seconds, runs it once, and only if the same page still has the keyboard. ⌘T, ⌘L, ⌘W, ⌘,, ⇧⌘T, ⌃Tab, ⌃⇧Tab, ⌘Q and Esc over a Crossbow overlay always stay with Crossbow; a rebound protected action keeps its protection. The choice is saved on this device only. **Native key capture, and whether the engine's unhandled-key report arrives for real pages and frames, have not been exercised** in a running build.

**New Document** opens a new tab in the active Space at the profile's document app, chosen in Settings → General → Browsing → **New Document opens in**: Google Docs, Sheets, Slides, Word, Notion, or a custom https address that is checked before it is saved. It is in the command bar and in Settings → Shortcuts, with no default chord; with no app chosen it offers **Choose a Document App…**. Whether those sites still serve their new-document addresses hasn't been checked. **Copy as Quote**, off by default under Settings → General → Selected Text, adds a page menu item for selected text. It copies the quote with the page's title and address, as plain text and as HTML, and uploads nothing. A selection in an embedded frame is quoted with that frame's address, and a frame from another site gets no page title. The address keeps its query and fragment but never a user name or password. It is tested with a stand-in pasteboard only.

Settings → Shortcuts → **Tab numbers** has two choices, saved on this Mac only. **Include Favorites in ⌘1–⌘8** is on by default. **⌘9 goes to** either the Last tab, the default, or the Ninth tab. Numbers count the sidebar's rows in the current Space, in its own profile, including unopened favorites and pins and skipping collapsed folders. A number with no row does nothing. With Ninth tab, the action is listed as "Go to Tab 9". The choices are tested in source; ⌘1–⌘9 through real key events have not been.

Settings → General → Quitting has **Warn before quitting**, off by default and saved on this device only. When it is on, ⌘Q, Quit in the app menu or Dock, and closing the last window ask "Quit Crossbow?". Enter quits, Esc or Cancel keeps everything open, and a second ⌘Q quits. Logging out, restarting and shutting down are never held up. When downloads are unfinished, paused ones included, the question says how many will be cancelled. It is tested in source with simulated frames; **the macOS quit hook has not run in the native app**.

Links sent to Crossbow by other apps (or passed as launch arguments) now open instead of being dropped: only `http`, `https`, HTML `file` and `crossbow` links are accepted, and logs name only the scheme and host. Settings → Links holds Arc-style routing rules (**URL contains** or **Host is** → a Space, checked in order, with a **Test a link** field) and a default destination (**Most Recent Space** or a chosen Space). A routed link opens as the first Today tab of that Space in its profile, and Crossbow comes forward; links arriving during first-run setup wait until it closes. A rule whose Space was deleted falls back to the default and is flagged. Rules are saved on this device only. The page also shows, read only, whether Crossbow is the system default browser, with an **Open System Settings** button; nothing in Crossbow changes the default. A development build (2026-10-28, synthetic data) received links from `open` while running and on launch, routed a **Host is** rule to its Space, used Most Recent Space for other links, refused `mailto:` without logging the address, and kept the tabs after quitting. **The Settings rule editor, bringing the window forward and the real default-browser query have not been checked natively**; Finder **Open With** for HTML files is not handled.

**Little Windows** are Crossbow's version of Little Arc: a small, separate window holding one page. Open one with **New Little Window** (⌃⌘N, the app menu or the command bar). It uses the Space chosen for new links and that Space's profile. Its toolbar has Back, Forward, Reload/Stop, the address (⌘L), **Open in Space…** (⌘O) and Close (⌘W). **Open in Space…** moves the live page into the chosen Space as its first Today tab. If that Space uses another profile, it first asks before reopening the page there; Cancel changes nothing. Closing a Little Window, or quitting, archives its page with its profile, so Reopen Closed restores it. Settings → Links → **Open links from other apps in a Little Window** (off by default, this device only) sends received links there instead of to a tab; routing rules still pick the Space.

A development build opened a Little Window from a link sent by another app, painted its page beside an unaffected main window, and archived the page with its Space and profile on an orderly quit. Typing, IME, pointer input, resizing, Open in Space and the close controls have not been checked natively yet.

Known limits:
- The window is always opaque, even when the main window uses its translucent background.
- Main-window shortcuts don't apply inside it.
- Right-click does nothing.
- Pages that open new windows load in the same window.
- Popups may be misplaced on a second monitor.

**Show All Little Windows** and **Close All Little Windows** are in the command bar (no default shortcuts); Close All archives each page like a single close. A later build showed the toolbar on the traffic-light row, matching the main window; the commands themselves have not been run natively.

Settings → Links also controls how Little Windows open and close. Every choice below is kept on this device only:
- **Open a Little Window from anywhere:** off by default. When on, ⌃⌥⌘N opens a Little Window from any app. You can record a different shortcut; ones Crossbow already uses are refused. The shortcut is registered with macOS without Accessibility permission. If another app already holds it, the switch stays off and says so.
- **⌥⌘-click:** on by default, as in Arc. ⌥⌘-clicking a link opens it in a Little Window in the clicked tab's Space and profile.
- **Shift-click:** on by default. Shift-clicking a link opens it in Peek over the current tab.
- **Archive Little Windows after:** Never, 1 hour, 12 hours (default) or 24 hours. It follows the tab rule, so the focused window and any window you've typed into stay open.

**Picture in Picture (source only):** when you leave a tab that is playing video with sound, Crossbow shows the video in its own floating player at the bottom right of the screen, with Play/Pause, back and forward 10 seconds, Mute, Back to Tab and Close (Close pauses the video). The player floats above other apps and over full-screen apps without taking focus, can be dragged and resized at 16:9, and remembers its position on this device. **Picture in Picture** is also in the tab menu and the command bar. Turn the automatic player off per profile in Settings → General → **Automatic Picture-in-Picture**. Muted autoplay never opens it. Little Windows get a pin button, **Keep Window on Top**. The web Picture-in-Picture APIs are turned off, so sites use this player instead. Videos inside frames, including embedded players from other sites, aren't detected yet. The source tab keeps painting at 30 frames per second while its player is open. All of this has been tested in source with simulated frames, and the video script in the system JavaScriptCore; native windows, real video and audio, and the effect of turning off the web APIs have not been run.

**Capture (source only):** press ⌘⇧2, choose **Capture** in the command bar or a tab's menu, or hold Command and Shift and drag over a page, in a tab, Peek or a Little Window. Drag to select an area (hold Space to move it), click or press Return for the whole visible page, or press Escape to cancel. The PNG is copied and, when **Save captures to Library** is on, saved to that profile's **Captures**, a tab in the Library panel (also **Show Captures** in the command bar) where you can open, copy, reveal, save or delete captures. A capture holds only the page's visible pixels, so it needs no Screen Recording permission; open select menus aren't included. Captures are kept apart from the library: they are neither backed up nor synced. Settings → General → Capture turns saving off per profile and Command-Shift drag off per device. Deleting a profile also deletes its captures: their files go first and their records only after, so a file that won't go keeps its record and the next launch finishes the job. If Captures can't be read, nothing is deleted and Crossbow says why. A damaged Captures file never stops Crossbow: Library → Captures offers **Move Aside**, which keeps the old file in the data folder and lists your capture files again, without their pages. Settings → Passwords is a **preview of a local password vault — not security reviewed; use test passwords only**, as its banner says. Damage and recovery:
- **Errors by cause:** damage in the file, wherever it is read, offers **Try Again**, which changes nothing, **Recover Passwords…** when the key is still in the Keychain, and a confirmed **Reset Vault…** last, or marks only the damaged entry, which can be deleted while the rest unlocks. A missing key or a key that doesn't match offers **Try Again** and a confirmed **Reset Vault…**. Only disk, permission and busy errors ask you to check permissions and disk space.
- **Checked when it opens:** a schema or page structure that isn't its format's is damage, with the recovery above, and opening never adds a table or a new vault id to an existing file. SQLite's own statistics tables (from `ANALYZE` or `PRAGMA optimize`) are not damage. A damaged page decides that the file is damaged, not which passwords are lost.
- **Newer files:** only a vault file whose format is newer asks for an update, and it offers no reset. Inside a current file, an entry or check value marked with another envelope version or key epoch is damage, not "newer": a damaged check value is rewritten when the key still opens your passwords, and a damaged entry can be deleted.
- **Recover Passwords…** copies every password that still opens with the key, and the sites saved as "never", into a new vault file under the same key, keeps the damaged file beside it, and says "Recovered N of M passwords", where M counts every distinct entry any read of the damaged file returned. It reads the table and its index each way, takes each entry from the read that finds it, and never lets one read remove a row another read returned, so in the tested vaults damage in a free page or an index loses none. When it couldn't read some of them, it says how many and names the kept file: in one test with two damages it says "Recovered 39 of 40 passwords. 1 couldn't be read". Damage can make M much too high: in one test a single damaged byte made it say "Recovered 40 of 198" when all 40 entries were recovered. M is too low if damage hides an entry from every read or makes two entries read as one, and then the message may not mention that entry; no single flipped bit did either in tests. Damage that hides entries from every read still leaves them out of the new vault: in a 40-entry test vault, a broken page type on the table's top page recovers none of the 40, and the message says 40 couldn't be read. Those entries stay in the kept file.
- **Reset Vault…** never deletes a Keychain key: it gives the vault a new identity, so other copies of the file, such as backups, stay readable. It also repairs a lost vault id, so the vault opens again without relaunching, and empties the list of sites saved as "never". It says the vault was reset only after checking the file it leaves.
- **Damaged files are kept:** a damaged file is never deleted. Reset or Recover Passwords moves it aside as `vault-damaged-<UTC time>.sqlite` in Crossbow's data folder, readable only by your user account, and the page names it once. Crossbow doesn't list such files later, except ones a stopped Recover left (below), and each still opens with the Keychain key.

A Recover that stops:
- A Recover that fails or is interrupted is undone, at once or at the next open, Recover or Reset. Crossbow decides whether a stopped Recover finished only by which file `vault.sqlite` is: still the original means it is undone, whatever happened to the kept name; the recovered file means it finished; anything else keeps the vault closed and names every kept file. It compares a stopped Recover's files by length and contents, so a data folder copied file by file still works. An undo moves files back only beside the very vault file it kept, unchanged; otherwise the vault stays closed, names every kept file and offers only **Try Again**, and nothing is written.
- If files Recover moved aside are gone, Crossbow finishes the Recover from its intact working file when it can. Otherwise the vault stays closed, and the page names the missing files and says to put them back, for example from the Trash, and choose **Try Again**.
- Recover's working file, `vault-recovery.sqlite`, is named with the kept files until the undo is complete, then deleted. Files a stopped Recover left are named on the Passwords page and in the next Recover's message.
- **While the page says the vault stays closed, don't move or delete the files it names:** they may hold passwords the vault file doesn't.
- Wherever the vault stays closed after a stopped Recover, the page offers **Open Without Them…**. It asks first, with **Cancel** as the default, then opens the vault file as it is. The files it names stay in the data folder; Crossbow never puts them back or writes over them, and names them on the Passwords page while they exist. Recover's working file is deleted. Once you chose **Open Without Them**, those files may hold passwords the vault doesn't, and Crossbow keeps naming them on the Passwords page until you delete them in Finder.
- Older source builds kept no record of a Recover, so after a Recover one of them stopped, Crossbow can't tell whether its kept files still belong with the vault file. The vault stays closed, the page says why and offers only **Open Without Them…**, and the named files hold passwords the vault file may not have: don't move or delete them, and copy the whole data folder somewhere safe before changing anything in it.
- Once the vault opens normally, a file the page names as left by a stopped Recover holds the damaged vault file as it was, with any passwords Recover couldn't read; like any other `vault-damaged` file, you can delete it in Finder when you no longer need those.

A reset in another window:
- A save, edit or delete after the vault was reset in another window is refused; the page locks and asks you to unlock again. A reset found by **Use in Current Profile**, a save card, a fill, **Reveal**, **Copy** or **Edit** locks the page and says so, as a refused save does.
- A refused save keeps an unsaved new entry, hidden, and says "Unlock again to save this entry." After **Unlock**, **Save** adds it to the new vault; **Discard Entry** drops it. Signing out, an account change, 5 minutes after your last input or leaving the page discard it, and the first three say so. A kept new entry is discarded 5 minutes after your last input, however the reset was found.
- An entry you were editing is discarded with its changes instead: "The vault was reset in another window. The entry you were editing was removed, so your changes were discarded."
- Two windows unlocking a new vault at once share one key instead of one replacing the other.

- **Clipboard:** a revealed password can't be selected or copied with ⌘C or ⌘X.
- **Secure keyboard input:** while the password field is focused and Crossbow is active, macOS secure keyboard input is on. It is released at once when Crossbow hides, another app becomes active, the window is minimised or another window takes the keyboard. Hiding the window keeps an unsaved draft.

The reviewed Ask AI checkpoint uses bounded non-streaming responses, a 45-second request deadline and one process-wide chat worker. It refuses invalid/oversized inputs, actual or malformed tools/function calls and incomplete outputs; absent/null/empty optional tool metadata does not invalidate ordinary text. Output is selectable plain text, not executable HTML or browser instructions. Limits are 16,384 bytes per message, 17 sent messages and 65,536 aggregate sent-content bytes, with no silent truncation. No automatic retries, model fallback, client launch or downloads. 628 regression tests passed in source after eight reproduced review repairs, including exact-profile recovery, cache-eviction entry recovery and composer scroll-state disposal. Bounded independent reviews of it are complete, and the last one found nothing left in its scope; no real model inference was exercised. Native send/cancel/retry/profile-boundary/layout/restart qualification remains blocked; source work is **not an update to the running preview**.

Explicit Send uses the saved loopback model and the existing limits, deadline and single-worker guard, without automatic fallback. Streaming requires one `text/event-stream` response content type, a normal stop, `[DONE]` and clean HTTP completion. Bounded, coalesced partial text is labeled incomplete, revalidates the original profile/account/destination, and never enters history or retry until successful completion. Error/cancel may retain already-displayed text, not necessarily the newest unread prefix; leaving/New Chat or invalid ownership erases it. **675 tests passed** in source after compact-composer, content-type and independent-review repairs. Initial BOM and CR/LF framing preserve text; narrowly inert metadata is supported without enabling tools or reasoning output. While streaming, the prompt and incomplete answer appear as display-only conversation rows. Simulated renderer checks preserve the answer's position mid-answer and at the bottom, including the narrow sidebar layout; empty/short fields fill the reserved composer height. Phase/error status has a polite accessibility region. Its final independent review found two minor layout problems; both were reproduced and repaired, with passing regressions and a full test run, but that last patch has had no further independent review. Two optional code cleanups remain deferred. Native controls, screen-reader announcements, layout, restart and actual model streaming remain unverified; no existing bundle contains this follow-up.

Settings → AI Providers also has **Browser features**. Each one is off by default, works only with the saved loopback provider and model, and is turned on per profile on this Mac. Turning one on shows what it sends and where; if you later change the provider or model, the feature pauses until you confirm again. The consent's version changed with the Translate text on 2026-11-01 and again with the Ask on Page text on 2026-11-03. Each browser feature you had turned on is off until you turn it on again and confirm its text: consent given before (versions 1 and 2) no longer counts.
- **Ask on Page:** press ⌘F, then Tab, to ask a question about the page from the Find field.
  - It sends your question and up to 12,000 bytes of the page's text, and says when that text was cut. The text can include parts you can't see, such as text scrolled out of view, in a scrolling area or covered by something else, and text you're writing in a page's editor, like an email or a document. It never sends what you type into form fields, the address, cookies, passwords or embedded frames.
  - It works only on http and https pages.
  - The answer appears in a card naming the provider. Cancel, Dismiss and Escape work as expected, and answers are not saved.
- **Tidy Downloads:** a finished download can suggest a clearer file name, using only the current name, the site's host and the file type.
  - Accept renames the file in place. It keeps the extension, avoids existing names and refuses if the file changed since the download.
  - Revert restores the old name until Crossbow quits.
- **Tidy Tab Titles:** pinning a tab, or choosing Tidy Title from a pin's menu, suggests a short title. You can Accept, Edit or Revert it. An accepted title is saved and syncs like a rename, and Restore Page Title clears it. A pin you renamed by hand is left alone.
- **Tidy Today:** from the command bar, or by right-clicking Today's divider, sort 3 to 40 Today tabs into up to 6 suggested folders.
  - A review sheet shows the folders before anything changes.
  - Folders are added to Pinned, so their tabs no longer archive automatically; the sheet says so.
  - Undo puts everything back, unless something has changed since.
- **Ask AI in the Command Bar:** when it's on, an "Ask {provider}" row follows what you type. Tab or choosing that row switches the field to Ask mode, and Return opens Ask AI and sends your text as the first message. Nothing is sent before Return. Text that looks like an address, a file path or a secret is refused with a reason, and stays in the field.
- **5-Second Previews:** hold Shift over a link for half a second to see a short summary of the linked page, labelled with the provider and "may be wrong". Leaving the link, clicking, scrolling or Escape closes it. Like every browser feature, it asks for consent again if it was turned on under an earlier consent text.
  - Crossbow loads the page in the background without your cookies, HTTP login, cache or Referer, so the site can't tie the visit to your account or the page you came from. It still sees this Mac's network address, and the request uses the profile's network settings, such as its proxy. It follows at most 3 redirects and checks each one.
  - Up to 6,000 bytes of the page's text go to the model, with its title, its description (up to 300 characters) and its host, but not its full address. Non-web files are never downloaded.
  - Local network addresses are refused, including names that lead to one and router names such as `.lan` or `.home.arpa`, unless the page and all its frames are at that same address (scheme, host and port). Each name is looked up first, and a failed lookup, or one that takes over a second, means no preview. The page's text is read away from the window, so a large page can't freeze the browser.
  - The browser looks the name up again when it loads the page, so a name whose answer changes in between (DNS rebinding), or a proxy, can still reach a local address. The consent card describes the fetch: that the site sees a visit from this Mac, what the visit leaves out, the local-address check and the lookup limit. Since 2026-11-01 the card also says that a site changing its address right after that check, or a proxy or DNS setting, can still make the fetch reach a device on your network. CEF reports no remote address for a request, so Crossbow can't close this gap.
- **Translate Pages:** when a web page loads in a language other than your Mac's first preferred language, a card offers **Translate**, **Never for {site}**, **Never for {language}** and **Close**. After a translation it offers **Show Original** and **Always Translate {language}**. **Translate Page** and **Show Original** are also in the command bar and, once the feature is on, the tab menu.
  - Text is replaced in place, as plain text, batch by batch. If the provider fails, the parts already translated stay and **Retry** is offered. Reloading or opening another page ends the translation. Going Back or Forward to a page the browser kept in its page cache brings it back with its translation and **Show Original**, however many pages the tab opened meanwhile. Among the last 8 pages left in the tab, a translation that was under way comes back as "Translation stopped" with **Retry**; from further back, it comes back with **Show Original**, and **Translate Page** translates what is left. Nothing is sent while the page is away. A link within the same page, or an address change the page makes itself, keeps the translation and **Show Original**, which restores the page's original text; text the page itself copied from translated text, such as a contents list or the window title, stays translated. With **Always Translate**, text the page adds is translated about a second after the page settles; otherwise choose **Translate Page** again.
  - Before you choose Translate, at most 600 bytes of the page's text go to the model, once per page load and only when the page doesn't name its own language; coming back with Back or Forward doesn't send it again, however long ago the page was left. This text, like the text sent after you choose Translate, can include text you can't see at the moment: scrolled out of view, in a scrolling area or covered by something else. After you choose it, a page sends at most 2,000 text nodes and 100,000 characters (UTF-16 units), however often it changes its own address. The browser enforces these limits for the page shown and the last 8 pages left in the tab, whatever the page's script reports. A page that comes back from further back brings its own totals, and whether its sample was sent, from Crossbow's script in that page, which the page's own scripts can't reach. When a translation reaches the limits, the card says only the first part of this long page was translated; when nothing more can be sent at all, it says the page reached the most text Crossbow translates for one page and that reloading it lets you translate it again. After **Show Original** and **Translate** again, the text is sent again.
  - It doesn't send the address, cookies, form fields, code or editors, or text marked `translate="no"` or `notranslate`. A page marked so on its root or body is never offered, and **Translate Page** says it asks not to be translated. Around a sensitive field it skips the form, the labels, the surrounding group, any label whose `for` names the field, a shadow host holding it or an element inside that host's open shadow tree, and every element that the field, its form or anything between them names by `aria-labelledby` or `aria-describedby`, however many ids the attribute lists. A sensitive field is a password field; a field whose autocomplete names a password, one-time code or card detail; a field named by the English card words the password vault's Fill Card uses; a frame inside a form, named for a card part, or named with a payment word or a payment processor's name in its title, name, id, label or address (such as Stripe's "Secure card payment input frame"; the list is English and can't name every processor); an editable area named for one or holding a card number; or any of these inside an open shadow root. A form or group with no text of its own reaches up to four containers up to the nearest one with text, never the whole page, though a card or password field placed directly in the page body keeps the whole page unread. A sensitive field outside any form also keeps unread the nearest container it shares with the field next to it, which in a single-page app can be the whole app. A field inside a closed shadow root isn't seen, so text beside it can be sent. It skips text hidden by display, visibility, low opacity, the clip property, clip-path, filters, masks, blend modes, text masking, a zero font size, a box under 8 px that clips its overflow, or a colour or fill under half opacity; text indented or placed off the page (above it, left of it, or past a right edge the page can't scroll to); and text scaled to almost nothing. Text covered by another element or below the fold can still be sent, and so can text in vertical writing modes past the edge, and text under wrappers inside closed shadow roots. Visible text under a clip path, filter, mask or blend mode, or with a gradient fill, is treated as hidden and isn't translated. Only language codes are logged.
  - These fixes (2026-11-01) are tested only in source, with a fake model and stand-in pages; no real model or the running app was used. The problems a second independent review found are fixed in source, except two kept as limits: fields inside closed shadow roots, and visible text under clip paths, masks, blend modes or gradient fills. A third review checked those fixes and found four problems left: a page coming back after more than 8 others, five more label layouts around sensitive fields, login and address offers drawn over a permission card, and a text node of only a Unicode space stopping the whole page. They are fixed in source and not yet reviewed again. Restoring from the page cache relies on CEF events that haven't been checked in the native app.
  - The target is always the Mac's first preferred language; Crossbow has no language setting of its own.
  - Choices stay on this Mac, per profile. **Reset…** under Translation choices clears them after a confirmation.
  - Since 2026-11-01 the Translate consent says the text sent can include text out of view.

All seven have been tested only with a fake provider and test pages served on this Mac. No real model has run them, and they haven't been used in the running app.

**Library backups and Restore Data (source only).** Crossbow keeps checked copies of its library database in a `Backups` folder beside it (`~/Library/Application Support/app.Crossbow.Crossbow/Backups/`, or `Backups` inside `CROSSBOW_DATA_DIR`). The folder is readable only by you (0700, files 0600), and backups never sync or upload.
- **When:** at launch when the newest backup is a day old (checked hourly while Crossbow runs), and just before Delete Sync Data, Turn Sync On, turning on or resetting encryption, Tidy Today's Accept, a library format upgrade and every restore. A failed backup never stops the operation; Restore Data lists it.
- **Kept:** the newest 7 daily backups, the newest daily backup of each of the last 4 weeks and the newest 10 made before an operation, within 500 MB in all.
- **What's in one:** Spaces, profiles, pins, folders, favorites, tabs, the archive, history, settings and sync state. Saved passwords, website data such as cookies and site storage, and downloads aren't backed up.
- **Restore Data…** in Settings → Advanced lists the backups with what each holds. It refuses a backup made by a newer Crossbow or a damaged one. After you confirm, it backs up the current library, then quits; the next launch puts the restored library in place before it opens. A profile whose website data isn't on this Mac starts empty, and Settings says so. It also refuses, before changing anything, when this library or the backup holds an item synced with the latest time Crossbow can record, because restored items couldn't replace it.
- **Clearing and deleting reach the backups:** Clear History removes that profile's history from every backup and from a restore waiting for the next launch, and deleting a profile removes its history and archive from them too. Each backup is rewritten the way it was written: a private copy beside it, changed with its freed pages wiped, checked and synced, then renamed over it. A backup that can't be cleaned is deleted, and Crossbow says how many; one that can't be deleted either is counted as still holding what was removed. **Delete All Backups…** in Settings → Advanced deletes every backup and a waiting restore after you confirm. Messages about backups name the Crossbow data folder, not its path, and offer Reveal in Finder where it helps. Partial copies left by a crash are deleted when backups are cleaned, and deleting a profile removes its site-permission choices from the library and its backups. Still open: Clear History is only partly fixed and can still leave some cleared rows readable in the live library file (10 of 3,000 cleared addresses in one test), and all of them while another connection is reading, after the window waits about 5 s; it reports every backup cleaned when the Backups folder can't be listed; and a deleted profile's "Never translate" sites stay in the library and its backups.
- **Sync after a restore:** this Mac keeps its own sign-in and encryption state, sync turns off, and nothing uploads until you choose Turn Sync On. Restored items then replace their synced copies, items added since the backup on any device are kept, and later changes win. A backup of an encrypted library uploads nothing unencrypted, to any account this Mac signs in to, until encryption is on for that account, with a new recovery code, or you choose to upload without it for that account.

This has been tested only in source, with disposable libraries and the in-process fake sync server. It hasn't been used in the running app.

**Signed updates (source only; not released).** A build has an updater only when it is compiled with `CROSSBOW_UPDATE_URL`, `CROSSBOW_UPDATE_KEYS` and `CROSSBOW_BUILD_NUMBER` (see [Build and run on macOS](../README.md#build-and-run-on-macos)). A build without one says so in Settings → General → Updates and offers nothing else.
- **Checking:** with **Automatically check for updates** on (this device only), Crossbow checks an Ed25519-signed feed once a day, with jitter, never in the first minute after the window opens and never while a check runs. Crossbow → **Check for Updates…** and **Check Now** in Settings → General → Updates check at once. Each feed carries a signed expiry, at most 30 days after it was published: an expired feed, or one older than a feed this Mac has already seen, never reads as up to date. The Updates group shows the last check and its result, and **Release Notes** shows an available version's notes.
- **Downloading:** a download is checked for its size, SHA-256 and archive signature, and the new app must carry a valid Developer ID signature and run on this Mac's macOS version. A download stops if it stalls, or runs past a deadline set by its size. **Cancel** stops it.
- **Installing:** an update installs on **Restart to Update**, or at quit with automatic checks on. While browser downloads are in progress, Restart to Update asks first, with **Restart Now** (which cancels them), **Wait for Downloads** and **Cancel**. After Crossbow quits, a small helper, `crossbow-update`, swaps the app bundles, starts the new version once and rolls back if that fails. Whether installing, rolling back or settling an interrupted install, Crossbow moves a bundle into the app's place only if it carries a Developer ID signature from the running app's own team. A new version counts as working 30 seconds after it first draws its window, or at a clean quit; after two starts that never got that far, the third rolls back. A release that was rolled back is never offered again. A copy of Crossbow opened during an install waits for the helper, then quits.
- **Ad-hoc builds,** such as the development builds this repository makes, never install an update themselves: they say why and offer **Show Download** instead, which first marks the download as coming from the internet (quarantine). Whether macOS then checks it when it is first opened hasn't been tested.
- **For maintainers:** `cargo xtask release-key --out DIR` writes an Ed25519 key pair outside the repository and prints only the public key. `cargo xtask release-sign` checks an archive as Crossbow will, including a Developer ID signature from the team given with `--team`, and writes the signed feed, valid for 14 days unless `--valid-days` says otherwise, and at most 30. A release must be signed again before its feed expires.

This is tested only in source, against loopback feeds with simulated signatures; it hasn't run in the native app, and nothing has been tried against a real Developer ID signature, Gatekeeper or notarization. Nothing has been signed, notarized, hosted or released, and no update feed exists yet. An independent security review found problems in rollback, feed freshness and ad-hoc builds; their fixes are in source (2026-11-03). A recheck of those fixes found two problems still open, both by reading the code and not yet reproduced, and fixes are in progress:
- Another program running under your account could put a link to a folder it controls where the updater keeps the previous version, write an install record, and have Crossbow swap that link into the app's own place at its next start.
- Such a program could also write an install record that makes Crossbow roll back at its next start to any older release its team signed, and then stop offering the current one.

Open requests on the roadmap include smooth sidebar resizing, correct desktop rendering, native glass, a functional equivalent for every Arc Settings option, and open provider choice with a Dia-inspired AI scope. AI is additive, not a replacement for the complete browser. The [Arc Settings parity table](arc-settings-parity.md) maps Arc's Settings options, related surfaces and requested additions, plus discovery gaps; its rows are not live-observed Arc controls. Source geometry tests and a static Settings inventory are not proof of live Arc parity.

Native UI refinement follows **Impeccable, Emil Kowalski and Hallmark 2.0.0 guidance**, inside the existing [design system](../DESIGN.md). Search shares field/result alignment metrics and surface-aware selected-text contrast. Favorites use a bounded four-column grid with internal scrolling, keyboard focus and at most two visible rows, keeping tabs and the Space switcher reachable. Normal and compact search/favorites journeys were observed in specific native development builds, which also found defects; some checks remain. A later source change does not inherit an older build's passes; web-only linting is not native UI evidence.

## Application icon

The bundled default is a flat black icon with a white Crossbow mark and a restrained edge highlight, without a gradient. The current Settings → Appearance implementation offers **Black, Graphite and Pearl**, a preview, **Apply**, **Cancel**, **Reset**, and a native **Choose PNG…** picker. Custom images must be square PNGs, 64–2048 pixels, at most 5 MiB. Pixels must be sRGB (untagged images are assumed sRGB); embedded ICC profiles and explicitly non-sRGB color metadata are rejected with export guidance rather than silently recolored. On macOS, personalization changes the running app's **Dock and application-switcher icon**, not the Finder icon inside the signed application bundle. ## Local responsiveness diagnostics

Set `CROSSBOW_FRAME_TRACE=1` when launching an **isolated native development build** to collect at most 10,000 UI passes. The app buffers samples in memory and writes `frame-trace-<pid>-<session-id>.json` under `CROSSBOW_DATA_DIR` on orderly exit. Collection is off otherwise. The private file uses mode `0600` on Unix and exclusive creation; no URLs, typed text, account identifiers or credentials are recorded. A crash/forced termination may leave no trace; a full buffer reports dropped samples rather than silently replacing them.

Recorded times cover CPU-side app UI/CEF-pump/Settings wall time, not rendered-frame presentation or input-to-visible latency. Frame/pass identifiers support multipass aggregation. The prior-frame eframe CPU value and the remaining event count are diagnostic context, not timing of a particular input. A bounded native Settings comparison had first-open outliers and unequal system load, and separately observed a popup-Escape defect. Stable sheet dimensions reduced measured p95 UI work in that comparison; **Arc parity and application-wide fluidity remain unverified**.

For debug macOS builds only, `CROSSBOW_INPUT_TRACE=1` logs at most 2,000 pointer-button, wheel and window-focus batches, plus window identifiers and whether Settings/search is open. It excludes text, keys, clipboard contents and URLs. It is off by default and intended for isolated fixtures, not normal browsing. These logs show event delivery, not input-to-presentation latency.

`CROSSBOW_FOCUS_TRACE=1`, also debug-macOS-only and off by default, records at most 2,000 raw/routing diagnostic records: aggregate keyboard/text/IME/clipboard event counts, logical focus, widget class, overlay presence and CEF editable-focus state. It does not record text, key identities, clipboard contents, URLs or profile/account IDs. Reaching the dispatch phase is not proof that the page received input.

For timed-archive QA only, debug builds accept `CROSSBOW_QA_ARCHIVE_AFTER_SECS=5` together with an explicit, disposable `CROSSBOW_DATA_DIR`. Values from 1–3600 seconds replace the configured age, not the real 60-second check interval; Settings → Never still disables archiving. Invalid/missing values use the normal hours setting, and release builds ignore this override. **Do not use it with your browsing library:** eligible fixture tabs really move to the archive. The override emits a content-free warning and is not a user-facing preference.

## Known limitations

- Full Arc feature parity is not established; Little Windows exist (one main window only; their shortcut, clicks and timer are not natively exercised), and Notes/Easels are not built.
- Chrome extensions are not supported, by decision (2026-11-01). Crossbow draws pages off-screen into its own window, and CEF's extension support works only in CEF's own windows. Built-in content blocking takes the place of ad-blocking extensions.
- Stock CEF does not provide proprietary codecs or Widevine; some media sites will not work.
- Identity providers may reject embedded browsers; a successful development OTP does not verify real email delivery or web-provider sign-in.
- Opening System Settings does not prove the default browser changed. When testing, don't change the default browser of a Mac you use for everyday browsing.
- Moving a Space to another profile closes its views and reopens them under the new profile rather than only changing metadata, so open pages do not keep the old cookie/session context. Tab moves across profiles are also rejected before mutating saved items, and search tab/favorite/pin candidates are restricted to the current profile. Web-view creation resolves the tab's owner rather than the currently selected space. These safeguards are not a complete isolation claim: synced ownership changes and native cookie/restart boundaries still need qualification.
- Browsing history is now stored by profile, including visit counts, page titles, command-bar suggestions and both Clear History controls. A background visit belongs to its tab's profile, not the visible space. Legacy global history has no reliable owner: its rows remain untouched in SQLite but are hidden from every profile rather than guessed or mixed into suggestions. Clearing a profile does not delete those unassigned legacy rows. New history writes and clears invalidate search results. A native development build passed the exercised cross-profile search boundary, both Clear History failure/retry controls, compact readback and cleared-suggestion restart checks. This is not complete account/profile isolation.
- CEF profile paths now use validated, collision-safe direct children of the canonical Chromium root (`Chromium/Profile-<hex-id>`); the previously nested `Chromium/Profiles/<id>` location could silently fall back to in-memory storage. Existing legacy directories are preserved, not migrated or deleted. Unusable profile storage must fail closed rather than open the global context. The same native development build preserved separate synthetic localStorage values across reload and full restart, without the prior path error. Cookies did not survive that restart while Chromium Safe Storage access was denied; encrypted cookie/password persistence remains unqualified. No Keychain denial bypass or plaintext fallback was added.
- The CEF IME handoff now supplies the required non-null InvalidRange. A native development build passed the exercised macOS US-layout accent preedit/commit in real page inputs at normal/compact sizes and in normal-size search. Cancellation and non-Latin candidate selection remain unqualified. The separate Find handoff repair distinguishes query clearing from dismissal and returns nested search to still-open Find. A later native development build passed the exercised normal/compact caret and range restoration, matched-result replacement and clear/retype/dismissal journeys, without DOM focus/caret injection. The IME argument fix alone was not a Find repair.
- Tab close/archive and restoration commit their SQLite changes before removing a live page or exposing a restored tab. A native development build passed injected close/restore/Reopen Closed failures and retries, compact Clear Today partial-success feedback with editable-form retention, and pin/space deletion guards when required closes fail. New archives now save explicit profile ownership: lists, Reopen Closed, exact-row restoration and retention (2,000 entries per profile) use that owner. Legacy ownerless rows remain untouched but hidden; changed/malformed source ownership is rejected rather than guessed. A later build passed exercised A/B list/reopen isolation and close/restore rollback/retry; the build after it passed deleted-source fallback into the same saved profile and native restart. Parent removal now uses the atomic path described below.
- Parent-item/space deletion now commits related tab closes, eligible Today archives and entity changes in one transaction. Folder deletion atomically reparents its direct children without closing their pages. Failed writes keep live views and saved rows unchanged; retry is safe. A native development build passed exercised normal/compact late-parent failures, cancel/retry, live drafts, shared-favorite selection, split survivors, profile-owned archive and exact-row full-restart checks. Malformed ownership and deferred-COMMIT faults have core regressions, not separate native passes. A later build passed bounded read-only engine requests while every window was offscreen, at normal/compact sizes, and retained native draft editing after restoration. - Timed auto-archive now conservatively keeps interacted live pages open for the lifetime of their web view, including across navigation/reload. The content-free guard is latched before potentially mutating pointer, wheel, key, text, IME and edit-command dispatch; harmless hover/focus/Find/copy/select-all/key-up do not latch it. Loading/crashed/unavailable live views are also withheld, as are active/visible panes, pins and favorites. Cold saved URL records have no live document and may still archive. The app reads current engine state rather than relying only on an earlier frame snapshot, and requests the next idle check. **This is not exact unsaved-form detection:** script-only state, manual-close/beforeunload handling and form restoration after quitting remain outside this safeguard. A native development build passed the exercised real-timer failure/retry, live-draft retention, untouched-tab selection, Never/menu-cancel and full-restart settings/archive checks using isolated synthetic data and the debug age override.
- Library blocks page keyboard input while open. Explicit Escape/X/toggle restores the previous owner; outside clicks retain their chosen page/widget target. Search/Settings replace Library. A native development build reproduced pointer-focus theft and incorrect Settings/Find Escape ordering; the next build then exposed typing into Find while covered by Settings. Current source separates pointer dismissal, gives Settings precedence and suspends the covered Find surface/input without deleting its query. A later build passed the exercised normal/compact hidden-input, popup/Settings/Find Escape, email-field cancellation, Library X/toggle/outside-click and unchanged-byte restart paths. Settings X and side-backdrop completion restore Find or page typing. A compact bottom-right click did not reach the raw app input trace and did not dismiss Settings; its native delivery cause remains unqualified. These bounded results are not complete overlay coverage.
- Removing an active or focused split pane selects a surviving pane without closing the detached tab. A native development build passed exercised active/non-active removal, compact two-to-one collapse and retained detached-tab form checks. Newer source checkpoints device-local split membership, pane order, divider ratios and the current visible pane's focus with the existing session state. Restore validates the saved profile and current Space/tab ownership, prunes stale members, and repairs invalid ratios without opening background web views. Failed tab writes withhold the newer layout; failed layout writes remain retryable. If a close commits before the layout does, restoration selects a validated survivor of the formerly visible split, including a final standalone favorite, without revealing a previously hidden split. SQLite reopen tests are not a native restart pass: split persistence qualification remains pending, and no existing bundle contains it. Named/pinned split groups and cross-device split sync are not implemented.
- **Repaint stability remains a qualification gate:** a native development build aborted in compact Settings with an egui 10-second lock timeout during a Chromium repaint callback. A bounded asynchronous dispatcher now removes synchronous CEF-to-egui lock coupling; controlled regressions reproduce the old failure mechanism and pass after repair. Two later builds passed bounded animated-page, Settings/Library and orderly quit/reopen checks without that timeout. This does not erase the earlier build's crash, reconstruct its exact first lock-holder/interleaving, prove long-running stability or establish Arc latency parity.
- Closing the developer tools window, or quitting Crossbow while it's open, crashes the app. In a development build on 2026-11-03 it happened at both closes and at the one quit tried; tabs and the password-saving switch survived each crash. A fix is in progress.
- Later source repairs add favorite drop slots, cancel off-sidebar/clipped drops, reject folder cycles before writing, separate mute/close targets and retry failed session writes. A native development build recovered from injected tab/UI-state write failures, automatically persisted the new tab and active selection after the faults were removed, and restored them after full quit/reopen. Permanent storage failure and crash recovery are not qualified. Per-space active favorites are now saved explicitly. Regression coverage is not a native check; a native development build reproduced failed active-favorite restoration before these changes.
- The importer is synchronous; a large library may stall the UI while it is applied.
- Responsiveness is an open problem and a blocking requirement, not final polish: current builds feel poor in hands-on use, and measured Arc-level latency and frame-consistency parity has **not** been established. Its requirements call for a native comparison and regression gates. The latest reported sidebar-resize stutter and tablet-like website rendering are under focused diagnosis; neither a viewport repair nor real desktop transparency (see [DESIGN.md](../DESIGN.md#native-desktop-transparency)) has been verified.
- Production distribution, signed upgrades, Windows/Linux operation, and complete account/profile isolation journeys have not passed native QA.
