# Browser identity and encrypted sync

## Status and non-negotiable boundary

This is the target architecture and acceptance gate, **not an implemented encryption or password-manager claim**. The current development browser uses custom email-code authentication and, against the development Worker only, a source-tested browser sign-in with Clerk (see [Implemented browser sign-in](#implemented-browser-sign-in)) that no real sign-in has exercised yet. By default `Store` constructs sync changes with `Encoding::Json`; naming an encryption enum in the wire protocol does not encrypt anything. No passwords may be added to that plaintext pipeline. An opt-in library-encryption foundation now exists in source (see [Implemented source foundation](#implemented-source-foundation)), but it passes none of the acceptance rows below.

The required end state is Clerk browser identity plus secure Cloudflare synchronization of bookmarks, folders/groups, Spaces, themes, selected settings and open-tab continuity across computers and future phone/iPad clients. Passwords require a separate end-to-end-encrypted vault. Local-only use remains possible.

## Trust boundaries

| Boundary | Responsibility | Must not become |
| --- | --- | --- |
| Clerk | Identity, sign-in, account recovery, session lifecycle and step-up authentication | Storage for vault keys, saved website passwords, browsing history or decrypted library data |
| Cloudflare Worker / D1 / per-account Durable Object | Authenticate devices, enforce account authorization, store ciphertext envelopes, sequence changes, handle revocation | An escrow for plaintext vault keys or an implicit cross-account merge service |
| Native client | Encrypt/decrypt, protect device keys, present trusted permission and account UI | A bridge that exposes browser secrets to websites, extensions, AI or untrusted page JavaScript |
| OS credential store | Wrap device secrets and support OS authentication | A guarantee against compromise of an already unlocked device |
| Waitlist | Optional early-access contact collection | Proof of browser sign-in, password recovery, or account enrollment |

Encrypted storage does not hide every access pattern. The service can still observe account/device identifiers, ciphertext sizes, timing and change counts. Minimize metadata, avoid URL-derived object identifiers, and document the residual exposure. A compromised unlocked endpoint remains a threat; do not promise immunity to malware or a hostile OS.

## Identity migration

1. Integrate the correct dedicated Crossbow Clerk application and separate development/production instances. Keep existing development API accounts usable until a reviewed migration exists.
2. Sign in using a provider-supported native flow and the existing system browser, not credentials typed into an arbitrary embedded webview. Use a vetted OAuth/OIDC flow with PKCE and state/nonce when supported; otherwise implement a reviewed one-use, short-lived browser-to-device exchange. A custom URL scheme alone is not proof of callback ownership.
3. Validate issuer, audience/authorized party, algorithm, expiry and the expected deployment. Obtain signing keys only from the configured trusted issuer, handle rotation, and fail closed when validation cannot complete.
4. Map immutable provider subject plus issuer to an internal account ID. Never silently merge accounts by matching an email address. Linking an existing library requires explicit informed confirmation and proof of both accounts.
5. Use short-lived, device-bound application authorization with secure refresh storage. Do not put tokens in logs, URLs, browser history, screenshots, diagnostics, SQLite library rows or synced preferences.
6. Apply sign-out, device revocation, account deletion and provider session invalidation to HTTP requests and active WebSockets. Verify cancellation during sign-in and resume after restart without exposing tokens.

The exact supported Clerk-native contract must be verified against the chosen provider configuration before coding a callback or advertising mobile support. No provider setup or migration has been performed by this document.

### Provider-native research checked on 2026-10-24

The [Clerk OAuth implementation guide](https://clerk.com/docs/guides/configure/auth-strategies/oauth/how-clerk-implements-oauth) and [official CLI example](https://github.com/clerk/cli-auth-example) document a candidate native path: a **public OAuth client with PKCE separately required**, `S256`, anti-CSRF state, and an OS-selected loopback port. The example registers `http://127.0.0.1/callback` and uses that path with the allocated port during authorization. This is a supported reference, not a configured Crossbow application or verified journey.

Do not copy the example's plaintext-file fallback or local-only logout semantics: Crossbow requires no production downgrade after unavailable/denied Keychain access, plus actual provider/device revocation. The current guide describes OAuth access tokens separately from Clerk application sessions; their verification and revocation contracts must not be treated as interchangeable. Public-client status alone does not enforce PKCE. Inspect the dedicated instance, discovery metadata, exact redirect matching, token type, audience/scopes, refresh lifecycle and revocation behavior before implementation. Do not embed a Clerk backend secret in the desktop binary.

### Implemented browser sign-in

Source-tested on 2026-11-01 against loopback fixtures only. Real Clerk, the deployed Worker's exchange and a real browser handoff are unverified.

- **Desktop (RFC 8252).** The app makes a PKCE `S256` verifier, a `state` and a `nonce` for each attempt and listens on `127.0.0.1` only, on 47231, then 47232, then 47233, with the exact registered redirect for the port it bound. All three busy is reported, not worked around. The sign-in page is handed to the system as any link, so the default browser opens it. When that is Crossbow, the page comes back as a link from another app and opens as an ordinary tab under the Links rules, in the profile of the Space they pick, where page features apply as on any page. RFC 8252 warns against an app capturing credentials through a view it controls; here the user's chosen browser shows the page, and the sign-in code never scripts, reads or watches the tab: only the loopback listener hears back. The listener answers one `/callback` and closes; another `state` ends the attempt without using any code. It waits 5 minutes. Cancel, or Escape on the Account page, closes it at once.
- **Exchange in the Worker.** The app sends the code, verifier, redirect and nonce to `POST /v1/auth/clerk`. The Worker redeems the code as a public client and reads only the ID token. Clerk's access and refresh tokens are discarded unread, and the app never receives any Clerk token. The Worker checks the algorithm, issuer, audience, authorized party, expiry and issue time with 60 s skew, nonce and subject, each as its own refusal. A token received directly from the token endpoint over TLS may skip signature validation under OIDC Core 3.1.3.7; the Worker validates the RS256 signature anyway through Web Crypto, with the issuer's key for the token's `kid`, and fails closed. Keys are fetched for each sign-in, so rotation needs no cache.
- **Identity mapping.** `(issuer, subject)` maps to an internal account id in `identities`. A known identity signs in to that account; its id never changes, so rows sealed with it stay readable. A new identity with a verified email that no account uses gets a new account. An email that an account already uses answers `link_required`; accounts are never merged by email.
- **Linking.** A signed-in account links an identity in two steps. The Worker holds a fresh browser sign-in for 5 minutes for that account and the session that asked; only that session can confirm it, once. The app names the browser sign-in's email, only if the provider verified it, and the account's, and binds only after **Link**. This proves both: the Crossbow session and a new browser sign-in. An identity bound to another account answers `identity_in_use` at either step.
- **Sessions.** A browser sign-in ends in the same Crossbow session as an email code: the same device row, a token stored as a hash on the server and in the Keychain on the Mac, and the same revocation. The Clerk session in the browser is not ended by Crossbow's Sign Out.
- **Configuration.** Only the development Worker has `CLERK_ISSUER` and `CLERK_CLIENT_ID`. Production has neither, answers `clerk_unavailable`, and its app shows email codes only.

### Implemented Delete Account

Deployed on the development Worker on 2026-11-01 and checked there with a disposable account: a wrong confirmation, a wrong code, then the right email with a fresh code, after which the session answered `401`. It isn't on the production Worker. The desktop app's side is tested in source only. Protocol: [Deleting the account](sync-protocol.md#deleting-the-account).

- **Step-up.** Settings → Account → **Delete Account…** asks for the account's email typed, then a code emailed to that address, at most 5 minutes old and used once. The Worker also accepts a fresh browser sign-in of an identity linked to the account; its rules are tested natively, but that path wasn't part of the check on the development Worker, and no app control sends one yet. A session alone never deletes an account.
- **What goes.** The account's synced rows and encryption marker, its devices, sessions, browser identities and held links, and the account row. Every sync socket of the account closes, so other signed-in devices stop.
- **What stays.** Sign-in challenges until the daily purge, the AI proxy's daily counter, and the Clerk user, which belongs to the provider. The UI says so before deleting. Cloudflare's own point-in-time recovery of D1 and Durable Objects is not addressed here, as for Delete Sync Data.
- **This Mac.** Nothing changes until the server confirms the delete, by `/v1/me` refusing the same session. Then the app signs out as Sign Out does and keeps its library.
- **Manage Account in Browser** opens the Clerk Account Portal's profile page, `https://<accounts host>/user`, with the host derived from the issuer as Clerk's `buildAccountsBaseUrl` derives it (the development instance's `/user` answered `200` when checked on 2026-11-01). It shows while signed in to an account with a browser sign-in linked, however this session signed in, and while `/v1/health` names such an issuer, and it goes to the system as sign-in does. Name, email and password changes happen there, in Clerk, not in Crossbow; Crossbow keeps nothing from that page.


## Encryption and key lifecycle

- Use reviewed, maintained cryptographic libraries and a versioned envelope format, not custom cryptography. Specify algorithms, nonce generation, authenticated metadata, version compatibility and size limits in test vectors before rollout.
- Generate a high-entropy account root key on a trusted client. Use key separation for the browsing library and the password vault, with independent per-purpose/per-epoch subkeys. Never derive the root key from a Clerk session token or an email address.
- Encrypt all sensitive library fields before enqueueing sync. Bind ciphertext to account, collection, object ID, schema version and key epoch using authenticated additional data; reject substitution across accounts or objects.
- Use fresh cryptographically secure nonces and authenticated encryption. Authenticate deletions and version/epoch transitions. Design replay/rollback and stale-device behavior explicitly; last-writer-wins by itself does not prevent replay.
- Store device private keys and local wrapping material through Keychain on macOS, appropriate platform secret storage on Windows/Linux, and platform key stores on future mobile clients. Define a safe unavailable/locked-key-store state; never silently downgrade to plaintext files in production.
- Local SQLite and backups also require a documented encryption strategy. Secure transport and encrypted cloud payloads do not protect a plaintext local password table. No plaintext passwords in WAL files, crash reports, swap-dependent claims, previews or diagnostics.
- Enrollment on a new device requires identity authentication **and** trusted-device approval or a high-entropy recovery secret. Show both devices and a verified confirmation code to prevent enrollment phishing. Merely signing into Clerk must not unlock the vault.
- Recovery must explain the trade-off before activation: identity recovery is not decryption-key recovery. Use an independently reviewed recovery design; losing every trusted device and the recovery secret can make data unrecoverable. Do not add hidden server escrow to avoid that warning.
- Revocation immediately denies further service access, closes sockets and rotates relevant keys for future data. It cannot erase secrets previously decrypted on a lost device. Test stale queued writes, delayed reconnects and key-rotation interruption.

### Implemented source foundation

Opt-in encryption for library sync rows is in `crates/crossbow-core/src/sync/e2ee.rs` and `key_store.rs`, with their callers in `app/src/sync_glue.rs` and `app/src/ui/settings.rs`. The envelope is described in [the sync protocol](sync-protocol.md#encrypted-library-rows-desktop-source-opt-in). Its native qualification steps are still pending.

It was built ahead of Clerk, which is a deliberate dependency-order deviation. As a result:

- **Account ids are bound into every sealed row.** The AAD contains the exact bytes of the internal account id and of the HLC text. The Clerk migration must map provider subject plus issuer to the **existing** internal account id, unchanged. Re-issuing or normalizing account ids, or changing the HLC encoding, would make every sealed row fail closed and needs a new envelope version.
- **Gaps against this document:**
  - Tombstones are not authenticated.
  - There is no device enrollment approval, revocation-driven rotation, key epoch 2 or escrow-free multi-device recovery beyond the recovery code.
  - There is no OS re-authentication before the code is shown.
  - Local SQLite is not encrypted.
  - A never-encrypted library still crosses to another account that signs in on the same device.
- **Verification so far.** It is verified only by source tests against an in-process fake server, an in-memory key store and simulated egui frames, plus independent source reviews. There is no native, real-Keychain, deployed-Worker or two-device evidence, and no external cryptographic review. None of the verification-matrix rows below are passed.

## Password-vault product gate

Implement and verify these as their own subsystem, not as another library entity:

- Local encrypted storage, explicit unlock/lock, idle timeout and screen-lock behavior.
- Save, update, reveal, copy, delete, undo policy and password generation. Sensitive actions require appropriate local reauthentication.
- Autofill bound to the actual requesting origin, frame and navigation state. Reject lookalike origins, untrusted cross-origin frames, hidden credential fields and insecure downgrades; define explicit user consent where automatic filling would be unsafe.
- Clipboard expiration must not delete newer unrelated clipboard content. Secrets never enter omnibox suggestions, AI inputs, page-accessible APIs, telemetry or ordinary sync logs.
- Import/export requires explicit confirmation, accurate scope, warnings about plaintext exports and isolated fixtures. Do not silently read the user's existing browser passwords.
- A visible device list, revoked-device rejection, enrollment and recovery tested end to end.
- An external security review and remediation before real password storage or public claims.

**Status (2026-11-01; development-build runs on 2026-11-03): preview, gate not passed.** A local vault now covers encrypted storage, explicit unlock/lock, an idle timeout, save/update/reveal/copy/delete, password generation, change-count-guarded clipboard expiry, non-destructive recovery (Try Again; for a damaged file whose key is available, Recover Passwords, which copies every entry that any read of the damaged file returns whole and that still opens into a new file under the same key, counts every entry any read returned, says how many it couldn't read and, when the reads disagree or stop short, that the file may have held more, and keeps the damaged file beside it; and last, a confirmed Reset that keeps Keychain keys and moves a file it can't fix aside), Secure Event Input on the password field, and repairs for the problems that independent source reviews of the vault, of page saving and filling, and of saved cards found, some of them only partly fixed (see after this list):

- **Damaged files.** Damage to the schema or page structure is read as damage, not as a storage error, and doesn't send every password aside when they are still readable. SQLite's statistics tables aren't damage. Opening never creates tables or a vault id in an existing file, and a format-2 file upgrades with its never-save list. Reset reports a reset only after checking the file it leaves. Recover takes each row, and the never-save list, from whichever read finds it, counts every row any read returns, and calls a read complete only if it saw all of them.
- **A stopped Recover.** An undo judges a stopped Recover by the vault file's identity, never a name, and compares its files by length and SHA-256, so a data folder copied file by file places as in place. While an undo can't finish or its files don't match its record, the vault stays closed, naming every kept file. If kept files are gone, Crossbow finishes the Recover from its working file when that file's bytes match the record; otherwise it keeps the vault closed and names the missing files. The working file is named while kept and deleted after a full undo and on Reset. A stop that left no record says what its files hold and offers nothing that can't work. Wherever the vault stays closed after a stopped Recover, Open Without Them, confirmed with Cancel as the default, opens the vault file as it is. It records the files as set aside atomically, never puts them back or writes over them, and names them while they exist.
- **Page fills.** `login.js` compiles and is run in tests in macOS's JavaScriptCore. The browser takes page logins only from frames whose current document reported the script installed, and an opaque document can't shed the browser's address-keyed records. Fills refuse filtered, masked, blended and tiny fields and mask border images, follow the flat tree through shadow DOM, need hit tests at a field's centre and a quarter of its box in from each corner, and stay in the focused field's own form or group. With no field focused, a login fills only when one form qualifies, and an address never fills. A saved address takes only visible fields, all shown on its offer card. Address and card fills ask the engine which fields are visible, and freeze where they go when their menu opens (below).

The latest review judged six problems only partly fixed: naming every file a stopped Recover left; the vault opening without a write-ahead log an undo couldn't move back, which a later undo could replay over newer writes; a saved address keeping parts from fields the user never saw; a fill from a focused field reaching a form a closed shadow root hides; fields slotted into a closed shadow root under a faint wrapper being filled, or read for addresses; and card fills in payment frames of another site, pending proof in the app. Two problems are documented rather than fixed: one vault serves every account and profile of the macOS user, and logins don't use the engine's visibility check (below). The latest repairs, for a stopped Recover whose files were copied or deleted and for card and address fills when focus moves within a frame or returns to one, have not been reviewed again.

A development build run on 2026-11-03 found an open problem beside the vault: Chromium's own form history keeps what pages submit, including usernames and address parts filled from the vault, unencrypted in the profile folder, where the vault's encryption doesn't reach. A fix is in progress.

**Page saving and filling (first slice): source tests and two development-build runs.** Behind a per-profile switch that is off by default, a page's trusted, user-activated login submit can offer to save; a key button fills a saved login only on request, only for the page's exact origin in the tab's profile, only into a frame whose current document's own origin is that origin, and only into fields that pass a visibility check (style, size, opacity, filters and masks along the flat tree, and hit tests at five points; transparent colours, and wrappers inside a closed shadow root, aren't checked), with a field focused only into that field's own form, and with no field focused only when one form on the page has such fields. This addresses part of the autofill row above. It does not meet it: there is no automatic fill, no related-site matching, no defence against a page feeding or reading its own values. It has run in Crossbow's renderer only in two development builds against the loopback login fixture, with a test key file in place of the Keychain, and never on a real page or against the real Keychain. The vault lacks screen-lock behavior, reauthentication, import/export, sync and device lists, has run natively only in those builds, and has had independent source reviews of the vault, of page saving and filling and of saved cards, with its latest repairs not yet reviewed again, and no external review. None of the rows above is passed.

**Saved addresses: source tests and one development-build run.** Behind the same switch, a trusted, user-activated submit of a form whose visible fields hold a street and a city or postal code can offer to save the address. Its parts are read only from fields that pass the fill visibility check as the form is submitted, so a field scrolled out of view isn't read, and the offer card shows every part Save keeps. The card ends 10 points above its pane's bottom: its parts scroll between its title and its Label, so Save Address, Never for This Site and Not Now stay on screen with every part at its limit, and Escape is Not Now for the focused pane's card whatever has focus (tested in simulated frames at 640×420 and 1360×860). Fill Address fills only on request and only from a focused field, in the page or a frame same-origin with it and all its ancestors. A frame of another site, or a frame below one, never gets an address: if it has the script, it has it for cards only (below). It fills only the focused field's form or, for a field outside any form, the fields outside any form in its nearest container below the body that holds another address field, and nothing elsewhere; with no field focused it fills nothing, even from the key button. **Closed shadow roots: the engine's answer, for addresses and cards (seen in Chromium only on the fixture page).** A field slotted into a closed shadow root has no `assignedSlot` the page's script can read, so the script's visibility walk never checks the wrappers inside that root. So an address fill, and a payment card fill, also asks Chromium, through IntersectionObserver v2 (`trackVisibility`, a 100 ms `delay`), whether each field is visible; the engine answers from what layout draws, closed roots included, and as specified answers no for any opacity below 1, a filter, a transform other than a translation or proportional scale, and anything drawn over the field. A fill waits at most 1,000 ms for an answer about every field it would fill. It fills nothing, and says so, if the focused field isn't visible, or if an answer is missing or the page has no IntersectionObserver v2; otherwise it fills only the visible fields and says how many it left empty. A saved address reads a field only if its latest answer, kept from the user's first click into the form, is visible. In tests the engine is a model in the stub page. CEF 154 carries the option, and in one development build on 2026-11-03 Chromium's answers gave the fixture page's seven cases their expected fills and messages, though the hidden values of two cases weren't read. Masks, clip paths and blend modes inside a closed root aren't in IntersectionObserver's specification. The fixture page `app/tests/fixtures/login/visibility.html` gives each native case's expected result, including the false negatives (an icon over a field, a floating label) the rule specifies. **Logins don't ask** (a documented limit): reveal buttons, icons in fields and fading forms would leave real logins empty. A login form slotted into a closed root under a faint wrapper is still filled from a focused field of its own, and, with nothing focused, when it is the only login form on the page. A login goes only to the origin it was saved for, which receives it at submit anyway and can read its own fields.

**Saved cards: source tests and one development-build run.** Settings → Passwords → Cards keeps a card's number, cardholder name, expiry and nickname per profile. The vault (format 8) seals each card in two envelopes: its details, which an unlock opens for the list, and its number, which is opened only to check it at unlock and for a fill, then wiped. A security code is never stored, asked for or filled. Cards are never synced or backed up. Pages never offer to save one, so the saving switch doesn't apply. Fill Card fills only on request, from the key button or a card field's context menu, with no further confirmation while the vault is unlocked. A card may go to a frame of another site than the page's, as a payment processor's fields need. It goes only to an https document, or an http one on this computer's loopback address for test fixtures. Every frame above it must be one too, and the document must be a secure context of that origin, as it said before any page script ran. The browser decides from its own frame tree and the address each frame committed. Under site isolation, a cross-site frame's renderer can't see its parent, so it leaves those ancestors to the browser, and a parent the browser can't find refuses the card. Such a frame gets `login.js` with the card functions only, so it never takes a login or an address. A fill reaches only the focused field's form. For a field outside any form, it reaches the nearest container below the body that holds another card field, else that field alone. It never goes beyond the field's frame, and with no field focused it fills nothing. It uses the engine's visibility answer (above).

**Card and address fills are frozen while their menu is open.** Opening the card menu freezes where the fill goes: the browser, frame and document, the origin the browser computed, the frame that has focus, and the numbered card note that names the focused field's form or group. `login.js` sends a note whenever focus moves within a frame to another card form or group, or, once a card field had focus, to anything outside one. Any change while the menu is open fills nothing and says "Nothing was filled: the page changed while the card menu was open." That includes moved focus, also to another card form in the same frame, a navigation or reload, a removed frame, and another tab, profile or window. A note still on its way when the card is chosen voids the fill in the renderer. The fill goes to the frame with focus while its current document has sent a card note, else the main frame, so a payment frame's field the user comes back to from another frame is filled, and a document reported again keeps its note count. A profile switch closes Add or Edit Card, wiping its values, and the Delete prompt. Fill Address uses the same frozen fill and numbered notes. These rules (2026-11-01) haven't been reviewed again. Testing is in source: `login.js` in JavaScriptCore against a stub page, the browser's rules over fake frames, and the page in simulated frames. One development build on 2026-11-03 filled a card into a visible payment frame from another origin on the loopback fixture, and nothing into a partly covered or faint one. That run didn't record whether the frame ran in its own process, so two behaviours are still inferred from CEF 154's headers, not observed: that CEF's browser-side frame tree gives a cross-process frame its parent and committed address, and that its focused frame names such a frame. No real payment page or Keychain has been exercised.

Passkeys and platform autofill extensions are separate work. A password-vault UI does not establish WebAuthn/passkey-provider compatibility, iOS Password AutoFill support or Android Credential Manager support.

## Page text and the local model: Translate, Previews and Quote

**Status (2026-11-01): source only.** Each feature is off by default, kept on this device and never synced; Translate and Previews are turned on per profile, and also need the shared consent in Settings → AI Providers → Browser features. They have had three independent reviews; the fixes for the third have not been reviewed again. Nothing here has run in Crossbow's renderer, on a real page, with a real model or against real DNS.

| Boundary | What crosses it | What must not |
| --- | --- | --- |
| Page script and Crossbow's page scripts | `translate.js` runs in each http(s) top frame's main world (the page's own JavaScript world) before the page's scripts, keeps the built-ins it uses, and reports only through a function the page never sees. It reads drawn text (which can be scrolled out of view or covered) and writes translations as text-node values only. | A record, list or report a page could alter, through a prototype setter or otherwise; markup parsed from a model's answer |
| Browser process | Takes each document's text and enforces its budget; asks the model; writes answers back to the document that sent the text | Page text in logs (only language codes are logged), the store, sync or Clerk |
| The profile's saved loopback model | The language sample, the text the user asked to translate, and a preview's page text | Page addresses, cookies, form values, or text near a password, card or code field. The model is an OpenAI-compatible server already running on `127.0.0.1`, reached with no proxy, redirects or credentials (`crates/crossbow-ai/src/local.rs`). It may itself forward what it gets, which Crossbow can't see |
| Pasteboard | Copy as Quote: the selection, the title and an address | Anything uploaded or stored |

**Translate.** The browser takes from each document at most one language sample (600 bytes of drawn text, only when the page doesn't name its language) and, over all its translations, at most 2,000 text nodes and 100,000 UTF-16 units, text sent again counting again. It enforces this itself, whatever the renderer reports, for the document shown and the last 8 the tab left (`app/src/translate.rs`), and the script keeps the same totals. A back/forward cache restore is a load, but the document gets back its own state and sends nothing it hadn't sent. Past those 8, the browser takes the returning document's state from its script, which includes it in its messages to the browser: whether its sample was sent, its node and unit totals (at most 2,000 and 100,000) and the pass it shows. The page's own scripts can't reach that state; a compromised renderer could understate it, but would gain no more than a reload already gives it. The script skips code, form fields, editors, `translate="no"` and `notranslate`, and, for a sensitive field, its form or group, its labels, labels whose `for` names it, its shadow host or an id in that host's open shadow trees, and every `aria-labelledby` or `aria-describedby` target of the field, its form and the elements between them:
- a password input;
- a field whose autocomplete names a password, a one-time code or a card part;
- a field the vault's Fill Card words name (`CARD_WORDS`, shared with `login.js`; a test checks the words, `wordRole`, the names read, the role constants, the number of labels read and the input types, allowing one difference: text reads the words on every select, the vault on single-choice ones only);
- a frame in a form, one named for a card part, or one named with a payment word or processor name (`PAYMENT_WORDS`) in its title, name, id, aria-label or address;
- an editor named for one, or holding a number that passes the Luhn check;
- a shadow host whose open shadow trees hold any of these.

A form or group with no text of its own reaches up to four ancestors for the one that has text, but never to the body. Text is read only if it is drawn, under the same hiding styles as the vault's fill check.

Residuals:
- A field in a closed shadow root is invisible to page script, so the text beside its host can be sent.
- Card words are English only.
- Text another element covers, such as a sticky header, can be sent, as can text below the fold. On a page written vertically, so can text placed beyond its edges.
- Visible text under a clip path, filter, mask or blend mode, or in gradient lettering, is never translated.
- Text the page copied from translated nodes stays translated after Show Original.
- Payment frames outside a form are recognised by English words and processor names; one named otherwise is read beside.
- A sensitive field outside a form next to another loose field keeps their whole shared container unread, which can be a single-page app's whole root (fails closed).
- Past the 8 documents a tab keeps, a returning document's sample flag and totals come from its own script (above).

**Previews.** Holding Shift over a link for half a second fetches the linked page in the linking page's profile, without cookies, cache or Referer, and through that profile's network and proxy settings. It follows at most three redirects, each checked. Before each request the name is looked up off the window's thread. The request goes ahead only if every address is public, unless the linking page and all its frames share the target's origin. Up to 6,000 bytes of the page's text, with its title, description and site name, go to the model, never the full address. The site sees a visit from this Mac.

**The local-address residual:** Chromium looks the name up again when it fetches. So a name whose answer changes in between (DNS rebinding), a resolver that answers Chromium differently, or a proxy can still reach a device on the local network. The consent text says so. Crossbow has no private profiles, so there is no private-profile rule to rely on.

**Quote.** Copy as Quote takes the selection CEF gives the context menu; no script runs in the page. It copies the selection as plain text and as an HTML block quote. The quote carries the frame's address, and its title only when that frame shares the page's origin. Nothing is uploaded or stored. The real pasteboard is unverified.

## Data model and synchronization

- Define stable IDs and ownership for Spaces, profiles, groups/folders, bookmark targets, pins and tabs. Distinguish persisted bookmarks from session state; clarify what is a profile boundary versus an account boundary.
- Do not sync cookies, site storage, authentication sessions, private-window state or sensitive local file paths by default. History and open-tab sharing need explicit scope and consent. Keep browser profile containers isolated locally.
- Encode encrypted changes with schema/key epochs, stable operation IDs and authenticated tombstones. Preserve offline work and idempotent retry. Detect incompatible schema/key versions without silently discarding records.
- Handle move/rename/delete conflicts without creating cycles, orphaning folders, resurrecting deleted objects or losing offline edits. Surface conflicts that cannot be resolved safely.
- A fresh device must reconstruct the correct hierarchy and ordering, then persist it across restart. A signed-out user must not see another account's cached library or pending writes.
- Device-local preferences stay local where appropriate. Sync font-family selections, not arbitrary executable URLs or unvalidated binary attachments.

## Required verification matrix

Use disposable accounts A/B, devices A1/A2/B1 and synthetic library/password fixtures. Keep real browsing profiles untouched.

1. Real Clerk sign-in, cancel, invalid/expired exchange, restart, sign-out, revoked provider session and wrong issuer/audience.
2. Create/rename/reorder bookmarks, nested groups and Spaces on A1; read them on A2; close/reopen both; confirm exact hierarchy and ordering.
3. Work offline on both; edit/move/delete the same objects; reconnect in both orders; verify convergence and no silent loss.
4. Inspect actual network/storage fixtures: sensitive plaintext absent from cloud payloads, local vault database/WAL and logs. Tampered envelopes, account swaps, replay, wrong epoch and corrupt ciphertext must fail closed.
5. Enroll A2 through the actual approval/recovery UI. Deny/cancel enrollment. Revoke A2 from A1, then verify HTTP/WebSocket denial and stale queued-write rejection.
6. Sign A1 out and sign B1 in. Check storage, caches, clipboard, suggestions, background jobs and queued sync for account crossover.
7. Password save/update/autofill/reveal/copy and clipboard replacement on local test origins, including deceptive and cross-origin fixture pages. Never use real passwords.
8. Recover a disposable account with no active device, then test an invalid recovery secret. Record exact data-loss and lockout behavior.
9. Independently run the journeys on macOS, Windows, Linux and each mobile delivery surface. Shared Rust code is not platform evidence.

No live provider or encrypted-sync acceptance row is passed by writing this design, compiling, using mocks, or testing the current JSON sync API.
